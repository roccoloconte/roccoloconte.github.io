LoRaWAN vs NB-IoT

August 14, 2025

LoRaWAN and NB-IoT solve the same fundamental problem - connecting low-power devices to the internet - but they take completely different approaches. LoRaWAN operates in unlicensed spectrum with a distributed gateway architecture, while NB-IoT runs on existing cellular infrastructure. Both have significant technical constraints that determine where they actually work.

LoRaWAN

Chirp Spread Spectrum

LoRa's physical layer uses a unique modulation technique called Chirp Spread Spectrum (CSS). Instead of transmitting data at a fixed frequency, LoRa chirps - sweeps frequency up and down in a specific pattern. This spreading makes signals more resistant to interference from other devices, able to travel longer distances at the same power level, and capable of operating below the noise floor (signals weaker than background noise).

The spreading factor trade-off is fundamental. LoRa uses spreading factors from SF7 to SF12, where each increase in SF halves the transmission rate and doubles transmission duration. SF7 provides fast transmission with shorter range and higher data rate, while SF12 offers slow transmission with longer range and lower data rate. We cannot have both speed and range at the same time.

Star-of-Stars Architecture

LoRaWAN networks follow a specific structure:

  • End devices (sensors) transmit to multiple gateways
  • Gateways forward packets to a network server via the internet
  • The network server manages the network and routes data to applications
  • Application servers process the actual sensor data

This architecture provides several advantages:

  • No single point of failure since if a gateway fails, devices can still reach other gateways
  • Excellent scalability because adding capacity means adding gateways, not replacing infrastructure
  • Ownership flexibility where you can own gateways or use public networks

Device Classes

Class A (Most common): Device sleeps most of the time, wakes up, sends data, listens briefly for responses, then goes back to sleep. Power consumption is in microamps when sleeping, but downlink latency can be hours if the device sleeps between transmissions.

Class B (Scheduled listening): Device wakes up at scheduled times to listen for messages, balancing power consumption with responsiveness. Use cases include devices that need regular commands but still prioritize battery life.

Class C (Always listening): Device listens continuously when not transmitting, providing lowest latency for receiving commands but highest power consumption. Not suitable for battery operation - use case is mains-powered devices like gateways or controllers.

The Collision Problem

LoRa networks face a critical problem called inter-SF collision due to the near-far effect. When a device close to the gateway transmits using SF7 (fast, short-range), it can drown out a distant device trying to communicate with SF12 (slow, long-range). This happens because transmission power matters more than spreading factor for interference - a strong nearby signal will overpower a weak distant signal regardless of their different SFs.

This creates serious deployment challenges:

  • We can't assume unlimited network capacity just because LoRa offers multiple spreading factors
  • Gateway placement becomes absolutely critical in dense areas
  • Sophisticated algorithms are needed to intelligently manage which devices use which spreading factors

Adaptive Data Rate

The network server monitors each device's signal quality and adjusts spreading factor (lower SF for good signal quality resulting in faster transmission) and transmit power (reduce power when signal is strong enough). The goal is to minimize airtime and power consumption.

Advanced ADR algorithms distribute devices across spreading factors more intelligently than basic approaches. Standard ADR optimizes individual devices, but advanced algorithms consider network-wide effects.

Security

LoRaWAN uses two separate encryption layers: network layer protects network management and device authentication, while application layer protects actual sensor data from network operators. Each device has unique keys that are derived during the join process, not stored permanently. Network and application providers cannot see each other's data.

LoRaWAN's current security relies on AES-128 encryption within a device-based key management system where keys are provisioned directly to devices. The LoRaWAN 1.1 specification significantly enhanced security over version 1.0.x by adding features like a separate Join Server, which further isolates keys and improves the overall security posture. However, the join process can still be exploited through replay attacks if developers don't implement the security protocols correctly.

Capacity and Scalability

In Europe, unlicensed band regulations limit devices to 1% duty cycle - meaning 36 seconds of transmission per hour maximum. Network capacity is fundamentally limited by total available airtime, not the number of devices.

The actual number of devices a gateway can support depends heavily on transmission patterns, message sizes, and spreading factor distribution. While simple airtime calculations might suggest lower limits, the statistical nature of transmissions (devices don't all transmit simultaneously) and the use of multiple channels and spreading factors allow gateways to serve much larger device populations in practice.

Mobility Limitations

LoRaWAN does not natively support seamless handover between gateways in the same way cellular networks do. This makes it less suitable for tracking assets that are continuously moving across gateway coverage zones, though it works fine for stationary or slowly moving devices.

Firmware Updates Over-the-Air (FUOTA)

While possible on LoRaWAN, firmware updates are extremely slow and challenging due to the low data rates and duty cycle limitations. Large firmware updates can take weeks or months to complete across a fleet, making this impractical for time-sensitive security patches.

Global Deployment Flexibility

LoRaWAN can be deployed by anyone, anywhere in the world (respecting regional ISM bands), making it ideal for remote locations or regions without cellular coverage. This deployment independence is a significant advantage in areas where cellular operators haven't established NB-IoT networks or where private network control is essential.

NB-IoT

Architecture

NB-IoT (Narrowband IoT) is fundamentally different from LoRaWAN because it's built on cellular infrastructure. It operates within existing LTE frequency bands (licensed spectrum), devices connect directly to cellular base stations with no gateways needed, uses simplified LTE protocols optimized for low-power, low-data IoT applications, and leverages existing cellular infrastructure and coverage.

Unlike LoRaWAN's unlicensed bands, NB-IoT operates in spectrum that mobile operators pay licensing fees for. This means no interference from garage door openers, WiFi, or other unlicensed devices; guaranteed quality of service backed by operator SLAs; and professional network management with 24/7 monitoring and maintenance.

This comes with significant constraints including higher ongoing costs where operators charge licensing fees plus per-device connectivity (typically $0.50-$2.00 per device per month depending on data usage and volume), operator dependency where you don't own or control the network, and slower deployment requiring operator approval, SIM provisioning, and contracts.

Power Saving Features

NB-IoT achieves long battery life through two key mechanisms:

  • Power Saving Mode (PSM) where the device can sleep for hours or days, appearing offline to the network
  • Extended Discontinuous Reception (eDRX) where the device wakes up periodically to check for messages

Battery life can extend to multiple years under optimal conditions, but real-world performance depends heavily on signal quality (retransmissions drain power), transmission frequency, payload size, and network configuration.

Coverage and Capacity

NB-IoT excels in difficult environments because it can maintain communication even when the signal is extremely weak. NB-IoT signals can penetrate deep into buildings, reach underground areas, and work in locations where other wireless technologies completely fail. Each NB-IoT cell tower can handle tens of thousands of connected devices thanks to optimized cellular protocols.

Mobility Support

NB-IoT provides seamless mobility support across cellular networks, making it ideal for tracking moving assets across wide geographic areas. Handover between cell towers is handled automatically by the cellular infrastructure. Where available, international roaming agreements enable device operation across multiple countries.

Firmware Updates Over-the-Air (FUOTA)

NB-IoT's higher bandwidth compared to LoRaWAN makes firmware updates much more practical. While still not as fast as traditional cellular connections, updates can be completed in reasonable timeframes for most applications.

Security

NB-IoT utilizes standardized 3GPP security protocols with SIM-based key management, providing cellular-grade encryption that includes AES-based algorithms. The key difference from LoRaWAN isn't the encryption algorithm itself, but the security architecture - NB-IoT uses established SIM card security with operator-managed authentication systems, while LoRaWAN uses device-based key provisioning.

Network Availability Limitations

NB-IoT deployment depends on cellular operator rollout, which is not yet globally ubiquitous. While coverage is expanding rapidly in urban areas and developed markets, rural or developing regions may lack NB-IoT availability. However, where available, NB-IoT benefits from existing cellular roaming agreements for international deployments.

When to Choose Each Technology

Choose LoRaWAN for:

  • Large outdoor areas with challenging RF conditions
  • Applications requiring private network control
  • Long-term projects where you want to own the infrastructure
  • Rural locations without reliable cellular coverage
  • Stationary or slowly moving devices
  • Cost-sensitive applications with many devices
  • International deployments in areas without NB-IoT coverage

Choose NB-IoT for:

  • Urban areas with strong cellular coverage
  • Mission-critical applications requiring guaranteed connectivity
  • Indoor use cases requiring deep building penetration
  • Applications requiring mobility across wide areas
  • Smaller device deployments
  • Projects needing faster deployment without infrastructure investment
  • Applications where operator-managed security and SLAs are essential
